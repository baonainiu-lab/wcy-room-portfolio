# 轨道造物师：建模与网站交互实施方案

日期：2026-09-22。当前状态：**人物形象未确定，按用户最新要求暂停角色接入。** 网站运行入口、界面与交互均不接入角色；现有几何角色试作源码、Blender 工程和 GLB 保留为待定资产，不代表人物方案已获确认。

下文是此前整理的候选制作路线与技术检查记录，不构成继续接入角色的授权。重新接入前须先由用户确定人物形象。

## 执行方式更新：由 Codex 完成制作

用户已明确要求使用 Codex 完成建模。因此后续建模、材质、绑定、渲染、导出及网页代码操作均按 Codex 经 Blender MCP / Python 和项目工具执行来设计，不以用户手工建模或外包建模师为前提。用户可提供审美反馈。

2026-09-22 已用 Blender 只读路径信息工具验证连接返回成功；这证明当前可访问 Blender，不证明人物建模质量已经达标。此次未修改 Blender 场景。

Blender 具备实现这类三维角色的制作能力，但 Codex 自动操作的最终还原度尚未验证，不承诺从生成图自动得到完全一致、所有角度都成立的可动画模型，也不预先声明还原百分比。主要不确定性是脸部曲面与神态、未展示区域的结构、动作时的变形以及网页实时材质效果。

阶段 A 以“头肩质量样模”为优先产物：由 Codex 制作真实头脸、眼球眼睑、发束与领口，输出参考视角、正面和侧面渲染，并在最小网页预览里检查三维转动。按脸部轮廓、眼睛形状与间距、发型剪影、头肩比例、表情五项对照。头肩样模完成后再判断当前方法能否达到期望，不用仅能加载的几何占位物代替美术质量验证。

若脚本生成的头脸经过迭代仍明显不符，记录具体差距并调整网格制作方法；图生 3D 或外部基础资产只能作为另行评估的辅助方案，不能假定其必然更相似，也不能隐藏必要的工具、成本或来源依赖。当前工具连接不代表已经具备图生 3D 服务。

Codex 的 MCP 外部工具接入机制见 [OpenAI 官方文档](https://learn.chatgpt.com/docs/extend/mcp)。该文档不对 Blender 人物建模的精度作保证。

## 推荐路线与首版目标

采用 Blender 制作原创人物，导出带骨骼与表情的 GLB，再接入现有原生 Three.js 网站。角色作为独立资产，保留现有房间浏览方式、标牌与内容面板。

首版体验：人物站在创作桌附近，轻微呼吸、眨眼，间歇使用折叠终端；访客靠近时人物看向访客；点击人物出现“关于我 / 看作品”两个入口；点击终端直接打开作品面板；现有三足机器人做简短回应。内容面板立即响应，不强制等动画播完。

首版定位为网站中的可交互角色。自由走动、寻路、布料物理、语音对话、实时口型属于后续独立扩展，当前先完成固定站位下的可靠互动。

## 1. 已核实的项目条件

- 现有依赖为 Three.js 0.172.0、GSAP 与 Vite，锁文件版本也是 0.172.0。沿用现有架构即可。
- 实际入口 `src/main.js:339` 仍加载 V4 房间及 V5、V6、V7 补充资产；V8 双烘焙流程仍在独立准备。人物控制器要兼容两者，实施时重新检查入口状态。
- V2 角色设定板位于 `docs/concepts/avatar-v2/character-sheet.png`，目前仅为图片，不是建模图纸或模型。它的透视、姿态及不同视图比例需统一。
- `src/main.js:477` 的 `configureBakedScene()` 会关闭阴影、隐藏所有灯、移除环境贴图并关闭色调映射，不能直接把需要实时光照的人物塞进房间遍历。
- `src/main.js:555` 的命中盒只建立一次；`:619` 的通用悬停会放大物件，默认到 1.8 倍。人物需要单独规则。
- 网站已有作品、关于和联系弹窗，但真实个人资料仍待补充。角色不能自动补出不存在的个人经历。

上述是代码检查结果；本方案中的预算、动作时长与结构是建议值，尚未经过模型和设备实测。

## 2. 建模前先形成统一图纸

从 V2 方案提取正面、侧面、背面，统一比例、衣服拼接、工具带走向、口袋位置和三格档案匣结构。采用自然 A 姿势，双手离开身体；终端、笔、包与机器人另画，不让道具挡住胸腹和手部结构。

标出五个核心辨识点：黑色雕塑块面短发、挑眉的表情、橙色立领、斜向工具带、三瓣机械花徽记。脸部单独提供正面与四分之三视角。没有真人资料时继续把它作为原创分身，不宣称复刻本人。

先做头肩灰模和全身轮廓，检查正面、侧面、背面、网站默认远景及一次近景。造型通过对照后再精做服装。头脸和轮廓优先于口袋缝线；少量确定的识别点，比增加大量挂件更有价值。

图生 3D 可选作粗体块参考，仍需检查脸部、手指、衣服下方与隐藏面，并重新处理可变形网格。推荐最终模型以 Blender 内可编辑的网格、UV、骨骼与材质为交付标准。

## 3. Blender 制作与交付规则

| 模块 | 制作方式 | 验收重点 |
| --- | --- | --- |
| 头脸 | 先雕刻体积，再制作适合表情变形的网格；眼球独立，嘴唇与眼睑有连续环线 | 微笑与闭眼不穿模；眼窝、眉弓和侧脸有真实体积 |
| 发型 | 使用数个有层次的大块面雕塑发束，保留发际线和顶部轮廓 | 四面都成立；远景也能认出；不依赖大量透明发片 |
| 身体、衣服 | 身体按遮挡关系精简；外套和裤子重点处理肩、肘、胯、膝的变形 | 抬手、握笔、俯身后无明显穿插与塌陷 |
| 鞋、徽记、工具带 | 独立制作后按需要绑定；缝线与微纹理优先放入贴图 | 大轮廓由几何表达，小细节不过度增加面数 |
| 折叠终端 | 屏幕、底座、铰链和笔独立；铰链设正确旋转轴 | 展开时不穿插；可单独命中；手持不漂移 |
| 三格档案匣 | 保持三个模块，建立腰部挂点 | 随身体移动；玻璃尽量使用低成本近似 |
| 机器人 | 首版优先复用场景里的三足机器人；需要 V2 精确外观时再独立替换 | 场景只出现预期数量的伙伴；腿和机身可分别动作 |

材质使用可导出的 PBR 结构：Base Color、Roughness、Metallic、Normal 与适量 AO。皮肤保留柔和色差，衣服呈现粗糙织物，硬件呈现金属反射。不要把固定姿势的强投影和光斑烘到人物底色里。

Blender 的复杂程序节点、毛发与渲染器特有效果不应被当作网页可直接重现的材质。将必要细节烘为贴图，并尽早在浏览器检查脸部质感、黑发层次与橙色饱和度。网页观感以实际运行画面验收。

Blender 源文件保存高精模型与网页模型两套 Collection，保留可修改源数据。单位统一，记录角色高度；在绑定前整理缩放与局部轴，不对已绑定骨架随意应用变换。站立脚底落在角色原点基准上。由 glTF 导出器处理 Blender 与 glTF 的坐标转换，浏览器只调整外层放置节点。

## 4. 骨骼、表情与动作

使用一套人形变形骨架，包含躯干、脖子、头、四肢、手指和眼球。可以采用控制骨架提高动画制作效率，导出时只保留必要变形骨与挂点，将 IK、约束等结果采样到实际骨骼动画。

眼睑与嘴部使用少量 Shape Keys：左右闭眼、微笑、眉部抬起与皱眉等。第一版约 6–10 个必要表情即可。绑定前完成主要拓扑，避免后续改点序导致表情失效。建议单顶点最多 4 个骨骼影响，导出后复查权重。

glTF 可承载骨骼、对象变换及形态键动画；导出模式和 Action 的组织方式应按本机 Blender 版本核验，不能照搬旧版 NLA 操作说明。每个动作导出后都检查实际 clip 名称与关联轨道。[Blender glTF 官方说明](https://docs.blender.org/manual/id/5.0/addons/import_export/scene_gltf2.html)

| 动作名（约定） | 内容 | 建议时长 / 触发 |
| --- | --- | --- |
| `idle` | 持终端站立、轻微呼吸与重心变化 | 6–8 秒循环 |
| `create_loop` | 看终端、落笔、停顿观察 | 5–7 秒循环或间歇播放 |
| `greet` | 抬眼、点头，持笔的手小幅致意 | 约 2 秒；进入或点击时播放一次 |
| `present` | 稍微展示终端，目光转向访客 | 约 2.5 秒；作品入口反馈 |
| `robot_ack` | 机器人机身倾斜、感应灯回应 | 约 1 秒；机器人点击反馈，可用现有对象动画 |

首版动作全部保持原地，不让骨骼动画移动网站的放置根节点。手、笔和终端在所有动作里保持合理接触。优先让笔继续留在手里，降低运行时换父级的复杂度。

眨眼与看向鼠标由角色控制器统一负责，避免与预制 clip 同时写入相同表情或骨骼。先更新 AnimationMixer，再叠加有限角度的头眼偏移；离开后平滑回到动画原始姿态。制作 `greet`、`present` 时暂时减弱程序化跟随，保护表演。

动作控制采用有限状态：
`loading → idle ↔ create_loop → greet / present → idle`。
切换使用约 0.2–0.35 秒混合；一次性动作结束后返回待机；连续点击不得叠加多个相同动作。弹窗开启、页面隐藏与减少动态效果设置分别有明确的暂停/简化规则。Three.js 的 AnimationMixer 用于播放片段并在渲染循环中按秒更新。[AnimationMixer 官方文档](https://threejs.org/docs/pages/AnimationMixer.html)

## 5. GLB 导出与资源组织

先导出不压缩的可验证 GLB，通过检查后再创建压缩版本。纹理与动画进入交付包；角色使用一个独立 GLB，复用的场景机器人可保持原有资产。网格、骨骼和节点名称稳定，后续优化不得损坏挂点与交互 ID。

建议节点：

```text
AvatarRoot                         # 网页放置、朝向与整体比例
└─ AvatarAsset                     # 导入 GLB
   ├─ Rig                          # 骨骼/动画根
   ├─ Face / Body / Outfit / Hair
   ├─ Socket_Terminal
   ├─ Socket_Stylus
   └─ Socket_ArchiveCase

交互 ID：
avatar.creator
avatar.terminal
avatar.archive
已有伙伴继续使用 robot_companion
```

上图只示意资产组成；终端、笔和档案匣的挂点在实际工程中必须跟随对应手部或腰部骨骼，或具有烘焙后的挂接轨道，不能仅作为无关联的根节点子物体。

对动态道具明确唯一控制来源：刚性父子挂点或骨骼动画任选合适方式，不同时由 GSAP、骨骼动画和每帧脚本争抢同一变换。

建议路径（下列新模型及模块尚未创建）：

manifest 记录高度、版本、哈希、骨架与 clip 名、交互节点、纹理和三角形统计，以及制作来源。版本号独立于 V2 概念图与房间版本。

使用 [Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator) 检查格式、引用、蒙皮和动画数据。零错误作为进入网站联调的条件；警告逐项说明。验证器通过不代表美术通过，还须导回 Blender 或独立浏览器查看器检查 A 姿势、每个动作、表情及材质。

压缩建议优先测试 Meshopt 网格压缩与 KTX2/Basis 纹理，并保留原始导出副本。当前本机 Three.js 0.172.0 的 loader 已有相应接口；运行时须显式配置解码器，KTX2 加载前调用硬件支持检测。不要仅转换文件而漏配 loader，或采用当前版本不支持的新扩展。[GLTFLoader 官方文档](https://threejs.org/docs/pages/GLTFLoader.html) [KTX2Loader 官方文档](https://threejs.org/docs/pages/KTX2Loader.html)

## 6. 网站接入设计

### 加载与生命周期

人物直接加入 `scene` 的独立根节点，不放进房间的批量材质处理和物件登场遍历。房间可先就绪，人物低优先级加载；成功后按当前日夜与 reduced-motion 状态初始化，播放一次简短问候。

预编译人物材质，避免第一次进入镜头时明显卡顿。加载失败不阻断作品和关于入口，在 DOM 区域提供已有透明 PNG 与相同内容按钮；不要把二维替代图宣称为可旋转模型。

控制器对外约定：
`update(delta, context)`、`setTheme(isDay)`、`setPointer(ndc)`、`play(name)`、`setPaused(paused)`、`getDebugState()`、`dispose()`。
销毁时停止动画，取消事件及定时器，释放人物独享网格、材质、纹理和解码器资源；共享环境与房间资源不由角色随意销毁。

### 光照与颜色

采用“烘焙房间 + 实时受光人物”的混合架构。在房间烘焙配置完成后，建立人物所需的环境贴图、少量柔和灯光。首版只用主光与柔和填充，控制新增渲染成本；房间的 unlit 材质继续保持原有光照。

如果人物使用 ACES 色调映射，先将已烘焙房间、地面和相应标牌材质显式标为 `toneMapped=false`，再处理全局 renderer 设置，逐一复查天空、自定义着色器及透明物件。避免将已有烘焙颜色再次做色调映射。若切换带来回归，先保留现有 NoToneMapping 并校准人物灯光强度，再单独处理人物高光。只设置人物 `toneMapped=true` 无法绕过全局 NoToneMapping。

日夜切换时同步调整人物光色和强度，时长与房间约 1.5 秒一致；人物材质不得进入房间的 `bakedMaterials` 色彩倍率集合。未来 V8 双烘焙接入时复用同一 `setTheme` 接口。

脚下优先使用随角色根节点移动的轻量柔影平面。现有房间关闭了实时阴影，且 MeshBasic 材质不会自然接收灯光阴影；若后续需要准确肢体投影，再加局部阴影接收层与更新策略，不直接开启整间房的实时阴影。

### 点击与动画

| 访客操作 | 人物/道具反馈 | 网站结果 |
| --- | --- | --- |
| 首次进入 | 抬头、点头或持笔致意一次 | 保持自由浏览，不抢镜头 |
| 鼠标靠近人物 | 眼睛及头部小幅跟随 | 显示简短提示 |
| 点击人物 | 轻微回应 | 显示“关于我 / 看作品”两个 DOM 按钮 |
| 点击终端 | 展示终端 | 立即打开现有作品面板 |
| 点击机器人 | 倾斜机身、感应灯回应 | 提示可探索的内容入口 |
| 切换日夜 | 人物光照同步变化 | 保持与房间一致 |
| 手机轻触 / 键盘激活 | 对应同一行为 | 不依赖鼠标 hover |

使用少量随根节点或道具骨骼移动的 box/capsule 代理。命中代理加入同一个候选列表，按实际距离与道具优先级处理。人物专门分支避开现有 1.8 倍缩放；出现重叠时做遮挡校验，避免隔墙点到人物。精确道具命中可使用递归 raycast，移动的模型不能沿用加载时的静态世界 AABB。

保留当前 6px 拖拽阈值和多指逻辑，使旋转房间与点击角色互不冲突。将 AnimationMixer 更新加入现有 render 循环，使用限制上界的 delta；页面恢复时重置时间，更新骨骼与代理后再做命中计算。

在现有 `.scene-accessibility` 中添加可聚焦的角色入口；Tab、Enter/Space 可完成同一任务，弹窗保留焦点管理，Escape 关闭并返回触发元素。减少动态效果时禁用自动问候、持续呼吸与目光跟随，内容按钮仍可用。

当前房间 OrbitControls 限制了观察象限。若增加“360° 查看角色”，另设角色查看模式，保存并恢复相机位置、target 和角度范围；不能把现有房间旋转直接当作完整人物环视。此项放在第二阶段。

## 7. 建议性能预算与验收

下表是首轮制作目标，不是硬件能力或已达到的成绩。机器人优先复用，不重复计入新增模型预算。

| 项目 | 桌面目标 | 手机目标 |
| --- | --- | --- |
| 人物含手持道具三角形 | 约 25k–45k | 约 12k–25k |
| 主要材质 | 尽量 4–6 个 | 尽量 3–4 个 |
| 新增 draw calls | 优先控制在 8–12 次内 | 优先控制在 6–8 次内 |
| 主贴图 | 2K 图集，必要细节按需分配 | 1K 图集起步 |
| 变形骨与表情 | 约 50–70 变形骨、6–10 表情 | 保留必要骨与表情 |
| 压缩后的角色交付包 | 争取 3–8MB | 争取 2–4MB |
| 新增实时阴影 | 首版柔影平面 | 柔影平面 |

材质数与 draw calls 不等价，拆开的网格可能重复绘制；以 renderer 统计值为准。下载体积也不等于显存占用。首版先建立基线，再按瓶颈处理贴图、透明材质、模型或动画更新频率。

现有项目期望高刷新体验。120 FPS 约为 8.33ms 帧间隔，只能在支持相应刷新率的设备上验证；普通手机以流畅的 60 FPS 为目标，必要时采用简化动作、降低 DPR 或静态替代。既有旧房间记录不能证明加人物后仍能达到目标。

现有性能插件主要包裹 `renderer.render()`，漏掉帧外部的 Mixer、跟随与代理更新，因此补测完整 update+render CPU 时间、可用 GPU 时间和实际 RAF 的 p50/p95。对照“无人物 / 静态人物 / 动态人物”三组，记录设备、窗口、DPR、浏览器、加载耗时、三角形、draw calls 和显存相关纹理统计。

验收覆盖：

- 脸、发型、衣服轮廓与设定图一致；默认房间尺度仍可辨识。
- 所有预设动作与表情无明显穿模，手持工具不漂移，脚底不滑。
- 日夜颜色协调；头脸可读，衣物和金属有层次。
- 点击人物/终端/机器人准确，拖拽不触发点击，原房间物件仍可用。
- 快速连点、动画结束、弹窗开关、切到后台后返回均能回到正确状态。
- 手机、键盘、减少动态效果、资源加载失败均可访问作品内容。
- 重新载入与卸载后无持续增长的资源占用；构建通过。
- 数据达到约定性能档位后再扩大交互范围。
